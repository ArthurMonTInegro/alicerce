# Testes

Quatro camadas, todas rodando no CI (`.github/workflows/ci.yml`) a cada push e pull request.

| Camada | Comando | O que garante | Situação em 15/10/2026, sem o privado (como no CI público) | Com o privado |
|---|---|---|---|---|
| Tipos | `npm run typecheck` | Os 4 projetos (engine, content, api, web) compilam em modo estrito; com o privado, os tipos dele também | sem erros | sem erros |
| Unidade | `npm test` | Motor, integridade do conteúdo, API, backup, contas, transição e limites da execução | 32 arquivos: 280 passaram, 3 pulados (só com o privado) | 282 passaram, 1 pulado (só sem o privado) |
| Soluções | `npm run test:solutions` | A solução oficial passa nos testes, o código inicial não passa, e a resposta de cada "prever a saída" é a saída real | 27 exercícios executáveis (níveis 0 e 1), 0 problemas | 290, 0 problemas |
| Ponta a ponta | `npm run test:e2e` | Fluxos reais num Chromium, em desktop e celular (Pixel 7) | 116 testes com `PAGES_DIST`: 86 passaram, 30 pulados (os só de desktop no celular, o de rolagem só no celular, e o JavaScript Premium, que precisa do privado), em 15/10/2026, já com a seção "Compromissos" de volta a `/planos` e os objetivos novos. Numa rodada anterior no mesmo dia, um teste de isolamento falhou porque clicou em "Executar" antes de o site reconhecer a conta; o teste passou a esperar por isso | `e2e/isolamento.spec.ts` no desktop: 20 passaram, 1 pulado (o caso sem o privado), inclusive o JavaScript Premium |

## Com e sem o repositório privado

O conteúdo das aulas dos níveis 2 a 14 fica num repositório privado (ver [PREMIUM.md](PREMIUM.md)). Sem ele, os testes de conteúdo e `npm run test:solutions` cobrem os níveis 0 e 1 e o mapa público do currículo (ids, etapas, habilidades), e a saída diz "modo público". Com ele (`premium/` ou `ALICERCE_PREMIUM_DIR`), cobrem as 111 lições e os 290 exercícios executáveis; `ALICERCE_EXIGIR_PREMIUM=1` faz a ausência do privado reprovar. O CI do repositório privado roda tudo no modo completo, mais `scripts/premium/verificar-vazamento.ts`. Os testes da API sobre o acesso ao conteúdo pago (`apps/api/test/access.test.ts`) usam uma aula paga falsa com ids reais do mapa, então rodam iguais nos dois modos; um bloco extra usa o conteúdo real quando o privado está presente. Também rodam nos dois modos o teste do verificador de vazamento (`scripts/premium/verificar-vazamento.test.ts`, com um privado falso de texto inventado) e a guarda estrutural `packages/content/src/sem-conteudo-pago.test.ts` (nenhum arquivo da árvore define lição, exercício, cartão, aprofundamento ou avaliação de aula paga).

## Unidade

- `packages/engine/src/engine.test.ts` (14): FSRS (intervalos crescem, lapsos reduzem estabilidade), domínio (dificuldade pesa, esquecimento rebaixa para "revisar"), grafo (ciclos, ordem topológica, estados), diagnóstico adaptativo e regras de dispensa.
- `packages/engine/src/progress.test.ts` (6): mesclagem de progresso entre aparelhos sem perder nada e saneamento de entrada hostil (`__proto__`, tamanhos, números fora da faixa).
- `packages/engine/src/tutor.test.ts` (4): o tutor offline nunca devolve a solução e reage ao tipo de erro.
- `packages/content/src/content.test.ts` (28): 15 níveis em ordem, ids únicos, todo pré-requisito existe e não há ciclos, etapas na ordem CONCEITO → REVISÃO, toda lição tem objetivos, termos em inglês e cartões, todo exercício tem dica, explicação e habilidade, múltipla escolha com exatamente uma correta e feedback em todas as opções, cada módulo tem prática de várias dificuldades, referências citadas existem e são usadas, projetos e diagnóstico consistentes, glossário sem duplicatas, dados de pesquisa com https.
- `apps/api/test/contas.test.ts` (25, servidor real com SQLite em memória): excluir a conta só com a senha atual (sem senha, sem gastar tentativa, senha errada, senha errada repetida até o 429, que vale também para o login, limite por IP entre contas, o IP de outra pessoa mandado como e-mail não bloqueia o login dela, sessão já encerrada, CSRF), "Sair de todos os aparelhos" (as outras sessões da mesma conta deixam de funcionar, outra conta não é afetada, só as sessões válidas são contadas, sessão já encerrada recebe 401), o maior progresso legítimo (gerado por `apps/api/test/maior-progresso.ts`) sincroniza, corpo acima do novo limite recebe 413, sem sessão ou acima do limite por conta o corpo grande é recusado antes de ser lido, cookie `Secure` conforme `NODE_ENV` e `COOKIE_SECURE`, e os scripts `start`/`dev` com `--env-file-if-exists=../../.env` (o teste confere o comando; o carregamento do `.env` em si foi conferido à mão).
- `apps/api/test/api.test.ts`: cabeçalhos de segurança e CSP do site, CSP própria da página de execução (`sandbox allow-scripts`, `frame-ancestors 'self'`, também com a URL codificada), `Cross-Origin-Resource-Policy: cross-origin` só no `runner.js`, nenhum CORS em `/api`, CSRF (inclusive com caminho codificado, como `/%61pi/auth/me`), cadastro e login, validação, limite de tentativas, mesclagem de progresso, exclusão de conta em cascata, tutor offline, tutor com IA só para contas e com limite diário, 404 da API, montagem da requisição ao Claude (a solução nunca é enviada) e tratamento de recusa.
- `apps/api/test/backup.test.ts` (17, dos quais 2 só rodam quando os testes rodam como root, como no build da imagem Docker; no CI, que não roda como root, eles são pulados): com arquivos de verdade num diretório temporário, sem simular o SQLite. Ensaio completo com o servidor real (`src/main.ts`) e os scripts rodados como na operação: contas criadas por HTTP que ainda estão só no `-wal` (a cópia ingênua do `.db` não tem nenhuma), backup com o servidor no ar, restauração recusada com o servidor rodando, restauração com ele parado, servidor de novo no banco restaurado (sessão e progresso voltaram) e volta ao banco anterior. Também: backup sem checkpoint no banco de origem; recusa de sha256 errado, `.sha256` ausente, arquivo alterado, corrompido e que não é banco; banco anterior guardado com `-wal` e `-shm` e volta a ele; `-wal` de uma queda guardado sem perder transação; backup automático antes de migração pendente e recusa de migrar se ele falhar; recusa de backup de esquema mais novo; nunca sobrescrever e retenção; retenção que não consegue apagar um antigo (o backup novo fica, e o script sai com 1); códigos de saída dos scripts e caminhos relativos; backup `0600` em pasta `0700`; restauração recusada que não toca no banco atual nem no `-wal` de uma queda; recusa de banco que é link simbólico ou pasta e de `--desfazer` com arquivo que não é banco guardado; `--desfazer` com o `-journal` de uma transação interrompida; mesmo modo do banco substituído. Como root: restaurar mantém o dono do banco (o servidor, com o usuário 1000, continua gravando), e o aviso quando quem restaura não é root; pasta de backups criada pelo root impede o backup automático do servidor, que não sobe e não migra.
- `apps/web/src/pages/Privacidade.test.tsx` (2): o texto de `/privacidade` sobre o tutor segue a regra do servidor: IA só para Premium ativo (cota zero no gratuito, em `PLANS`), limite diário e mensal, e as mensagens anteriores da conversa também vão ao provedor.
- `apps/web/src/features/runner/limits.test.ts` (8): o teto na fronteira com a página de execução: saída de 1 milhão de caracteres cortada com aviso, erro, traceback e passo a passo gigantes, nomes de variável que não poluem o protótipo, formato inesperado recusado, resultado SQL e JavaScript.

## Soluções

`scripts/verify-solutions.ts` executa, no CPython local, o mesmo `harness.py` que roda no navegador. Para exercícios de código e de correção, a solução tem de passar nos testes e o código inicial tem de falhar (senão o exercício não ensina nada). Para SQL, a consulta de referência tem de rodar e a inicial tem de dar resultado diferente. Para "prever a saída" em Python e JavaScript, o programa é executado e a saída real tem de ser exatamente a resposta cadastrada. Um exercício que falha aqui não entra no conteúdo.

## Ponta a ponta

`e2e/fluxos.spec.ts`: navegação sem erros de console, as 8 etapas de uma lição com conclusão, Python executado de verdade no laboratório, erro traduzido e explicado, JavaScript na página de execução isolada, diagnóstico completo, cadastro com sincronização e saída, tutor recusando entregar a resposta (pedida de dentro de um exercício de código do nível 1: recusa, dá a próxima pista e nenhuma linha da solução oficial aparece), 404 amigável e HTML pré-renderizado legível sem JavaScript.

`e2e/a11y.spec.ts`: axe-core com regras WCAG 2.2 AA em 16 páginas e nas etapas Explicação, Exercícios e Desafio de todas as lições (lista lida do sitemap), contraste no tema escuro e ausência de rolagem horizontal no celular em todas as páginas principais.

`e2e/isolamento.spec.ts` (só no projeto desktop): ataques do código do estudante contra a conta logada, em JavaScript e em Python (`DELETE /api/auth/me`, `GET /api/auth/me`, `PUT /api/progress`, logout e tutor, com `fetch` com e sem `credentials: 'include'`, `XMLHttpRequest`, `pyodide.http` e `import()`, sempre com `x-alicerce: 1`), conferindo que a conta, a sessão e o progresso ficam intactos, que o e-mail não aparece e que nada sai com o cookie; o mesmo ataque com a CSP desligada (`bypassCSP`), em que só a origem opaca protege; `localStorage`, cookies, IndexedDB e `parent.document` inacessíveis; a página de execução aberta diretamente ou emoldurada por outra origem não executa; laço infinito em Python e em JavaScript estoura o tempo e a execução seguinte funciona; tarefa `asyncio` não sobrevive à execução; falha no download do Pyodide (`page.route`) e wasm corrompido seguidos de sucesso; saída de 1 milhão de caracteres cortada com a página respondendo. Acrescentados na revisão: `WebSocket`, `EventSource`, `importScripts`, worker com URL do site e `POST` `no-cors` sem `x-alicerce` (com e sem CSP); o que acontece na thread do iframe (`window.open`, `top.location`, formulário, imagem, navegação do próprio iframe sem cookie, segundo "pronto" ignorado); formulário de uma página do mesmo site (outra porta) contra logout e tutor, também com caminho codificado; resultado forjado pelo próprio código do estudante, gigante ou malformado; link do laboratório que troca a função de correção não altera um desafio feito depois na mesma aba, nem quando o desafio é testado com a execução do link ainda em andamento; queda do worker do Python por um callback e enxurrada de mensagens seguidas de execução normal. Depois da integração com a cópia: o limite de dentro dos workers (`harness.py` e `output-limit.ts`) para o programa com aviso, e uma escrita que o contorna em Python ainda é cortada na fronteira; o `PUT /api/progress` do ataque leva o `expectedUserId` certo da conta (e o mesmo corpo é aceito da origem do site), para que só o isolamento o barre; e um exercício de JavaScript de lição Premium, com o plano concedido no banco descartável, é corrigido e roda na página de execução: esse teste só roda quando o servidor do e2e tem o repositório privado (`/api/health` com `conteudoPago: "disponivel"`, por `ALICERCE_PREMIUM_DIR` ou `premium/` na raiz), porque os níveis 0 e 1 não têm exercício de JavaScript; sem o privado, como no CI público, ele é pulado com esse motivo e roda no lugar dele o teste da recusa (Premium ativo recebe 503 e o aviso de conteúdo indisponível, sem nenhum exercício). Uma mensagem de erro gigante, em Python e em JavaScript, e um resultado SQL gigante não deixam tarefa longa na página do site (`PerformanceObserver` de `longtask`); `apps/web/src/features/runner/errors.test.ts` mede o mesmo na explicação dos erros.

`e2e/pages.spec.ts` (só no projeto desktop, e só com `PAGES_DIST` definido): o build estático do GitHub Pages servido por `e2e/servidor-pages.ts`, um servidor que imita o Pages (sem CSP nem outros cabeçalhos de segurança, `Access-Control-Allow-Origin: *` em tudo; isso é suposição sobre o Pages, não medição). Confere que um exercício de Python de uma lição gratuita roda e é corrigido, que JavaScript roda no laboratório (o build público não tem exercício de JavaScript: estão nas lições Premium, que só o servidor entrega, e a correção de um deles está em `isolamento.spec.ts`, com uma conta Premium), que o código do laboratório fica sem rede e sem os dados do site, que a página de execução aberta direto ou emoldurada por outra origem não roda, e que uma página que emoldura o site e troca a página do iframe de execução não recebe o canal. Para rodar:

```
BASE_PATH=/alicerce/ VITE_STATIC=1 npm run build && cp -r apps/web/dist /tmp/alicerce-pages && npm run build
PAGES_DIST=/tmp/alicerce-pages npx playwright test e2e/pages.spec.ts
```

O CI faz o mesmo: monta o build estático numa pasta à parte antes do build de sempre e passa `PAGES_DIST` ao `npm run test:e2e` (a mudança no `ci.yml` ainda não rodou no GitHub).

Para rodar localmente, faça `npm run build` antes; o Playwright sobe o servidor sozinho, com banco descartável em `test-results/` e sem chave de IA.

## O que não é testado automaticamente

- O tutor com IA contra a API real (os testes usam um cliente falso que captura a requisição). Testar com chave real gasta dinheiro e depende de rede.
- Leitores de tela reais (NVDA, VoiceOver). O axe pega problemas estruturais, não a experiência completa.
- Links externos: `scripts/check-links.ts` confere as 129 referências, mas depende de rede aberta e não roda no CI (no ambiente da verificação de 14/10/2026, o `fetch` do Node não resolveu nenhum endereço, e as 129 deram erro de DNS: os links não foram conferidos).
- A imagem Docker: o Dockerfile foi validado simulando o estágio final, sem um daemon Docker disponível.
