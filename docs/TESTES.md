## Com e sem o repositório privado

O conteúdo das aulas dos níveis 2 a 14 fica num repositório privado (ver [PREMIUM.md](PREMIUM.md)). Sem ele, os testes de conteúdo e `npm run test:solutions` cobrem os níveis 0 e 1 e o mapa público do currículo (ids, etapas, habilidades), e a saída diz "modo público". Com ele (`premium/` ou `ALICERCE_PREMIUM_DIR`), cobrem as 111 lições e os 290 exercícios executáveis; `ALICERCE_EXIGIR_PREMIUM=1` faz a ausência do privado reprovar. O CI do repositório privado roda tudo no modo completo, mais `scripts/premium/verificar-vazamento.ts`. Os testes da API sobre o acesso ao conteúdo pago (`apps/api/test/access.test.ts`) usam uma aula paga falsa com ids reais do mapa, então rodam iguais nos dois modos; um bloco extra usa o conteúdo real quando o privado está presente. Também rodam nos dois modos o teste do verificador de vazamento (`scripts/premium/verificar-vazamento.test.ts`, com um privado falso de texto inventado) e a guarda estrutural `packages/content/src/sem-conteudo-pago.test.ts` (nenhum arquivo da árvore define lição, exercício, cartão, aprofundamento ou avaliação de aula paga).

## Soluções

`scripts/verify-solutions.ts` executa, no CPython local, o mesmo `harness.py` que roda no navegador. Para exercícios de código e de correção, a solução tem de passar nos testes e o código inicial tem de falhar (senão o exercício não ensina nada). Para SQL, a consulta de referência tem de rodar e a inicial tem de dar resultado diferente. Para "prever a saída" em Python e JavaScript, o programa é executado e a saída real tem de ser exatamente a resposta cadastrada. Um exercício que falha aqui não entra no conteúdo.

## Requisito dos testes como root

Dois testes de `apps/api/test/backup.test.ts` só rodam como root: eles dão a pasta e o banco ao usuário 1000 (o `node` da imagem Docker) e rodam o servidor com ele. Precisam de um root de verdade, capaz de trocar o dono de um arquivo para outro usuário, como no build da imagem Docker. Fora do root (no CI do GitHub, por exemplo) eles são pulados.

Num sandbox que roda o processo como root dentro de um namespace de usuário que só mapeia o próprio uid, o `chown` para 1000 falha com `EINVAL`. Foi o caso do relatório do Codex: 320 passaram, 2 falharam com `chown EINVAL`, 3 pulados. Em 23/10/2026 o caso foi reproduzido aqui com `unshare --user --map-root-user npx vitest run apps/api/test/backup.test.ts`: os mesmos 2 falharam com o mesmo erro e os outros 15 passaram. Sem o namespace, como root, os 17 passaram. É limitação do ambiente, não defeito do backup. Os testes continuam falhando nesse caso, mas a mensagem agora diz o motivo: "Ambiente sem o usuário 1000".

Nesse mesmo namespace, a restauração de um banco cujo dono não está mapeado também foi tentada. Ela para antes de tocar no banco: ou na conferência de uso, ou com `EINVAL` no `chown` com `--mesmo-em-uso`. O sha256 do banco não mudou, e não sobrou arquivo temporário. A recomendação de [OPERACAO.md](OPERACAO.md) continua: restaure com o mesmo usuário do servidor, ou como root de verdade.

## Navegadores

Os testes ponta a ponta rodam só no Chromium, o único navegador instalado neste ambiente (`/opt/pw-browsers`) e no CI (`npx playwright install --with-deps chromium`). O projeto `celular` é o mesmo Chromium emulando um Pixel 7 (tela, toque e agente de usuário), não um navegador de celular de verdade. **Firefox e Safari (WebKit) não foram testados**; nada aqui garante que os fluxos funcionem neles.

## O que não é testado automaticamente

- O tutor com IA contra a API real (os testes usam um cliente falso que captura a requisição). Testar com chave real gasta dinheiro e depende de rede. A rodada com o modelo real, a revisão humana e a medição de custo e latência estão prontas em [TUTOR-AVALIACAO.md](TUTOR-AVALIACAO.md) e esperam autorização do consumo.
- Firefox, Safari e navegadores de celular de verdade (ver "Navegadores").
- Leitores de tela reais (NVDA, VoiceOver). O axe pega problemas estruturais, não a experiência completa.
- Links externos: `scripts/check-links.ts` confere as 129 referências, mas depende de rede aberta e não roda no CI (no ambiente da verificação de 14/10/2026, o `fetch` do Node não resolveu nenhum endereço, e as 129 deram erro de DNS: os links não foram conferidos).
- A imagem Docker: o Dockerfile foi validado simulando o estágio final, sem um daemon Docker disponível.
