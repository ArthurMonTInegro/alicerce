> Execução do código do estudante (UP03): os workers não rodam mais na origem do site, e sim numa página de execução de origem opaca (ver "Execução de código do estudante"). Isso foi medido e testado só no Chromium; Firefox e Safari não foram testados. Os limites de saída (no worker e na fronteira com o site) contêm o volume do que volta, mas não limitam a memória que código arbitrário consegue usar.

# Segurança

Modelo de ameaças resumido: a plataforma executa código escrito por estudantes, guarda contas e chama uma API paga. Os riscos principais são código do estudante escapando do isolamento, roubo de sessão, abuso de login, abuso de custo do tutor e entrada maliciosa no progresso sincronizado.

## Execução de código do estudante

**Nada roda no servidor.** Python, JavaScript e SQL rodam no navegador de quem escreveu o código. O servidor nunca executa código enviado.

### O problema que o isolamento resolve

Até a página de execução isolada existir, os workers de Python e JavaScript eram criados pela própria página do site e tinham a **mesma origem** dela. Um worker não enxerga o DOM nem `document.cookie`, mas o `fetch` dele leva o cookie HttpOnly da sessão (`alicerce_sessao`, `SameSite=Lax`) e lê a resposta, e a defesa contra CSRF é só o cabeçalho fixo `x-alicerce: 1`, que qualquer código consegue enviar. Bastava `await fetch('/api/auth/me', {method: 'DELETE', headers: {'x-alicerce': '1'}})` no laboratório para apagar a conta; dava também para ler o e-mail, trocar o progresso (`PUT /api/progress`), gastar a cota do tutor e abrir o IndexedDB do site. O Pyodide chega ao `fetch` pelo módulo `js`. Um link compartilhado do laboratório (`#codigo=`) fazia isso com quem clicasse em Executar.

### Como funciona agora

- **Origem opaca.** Todo código do estudante roda na página de execução (`apps/web/public/runner.html` e `runner.js`), que o site carrega num `<iframe sandbox="allow-scripts">` **sem** `allow-same-origin` (`apps/web/src/features/runner/sandbox.ts`). A origem dela é `null`: os pedidos que saem de lá não levam o cookie da sessão, as respostas da API não podem ser lidas (a API não libera CORS) e `localStorage`, `document.cookie`, `indexedDB`, `caches` e `parent.document` dão `SecurityError`. Sem `allow-popups`, `allow-top-navigation` e `allow-forms`, o iframe também não abre janelas, não navega o site e não envia formulários.
- **Workers dentro do iframe.** O código não roda na thread do iframe: roda em workers criados lá a partir do texto que o site manda, como URL `data:` (numa origem opaca, um worker com URL do site é recusado, e um worker de `blob:` do tipo módulo falha no Chromium). Um laço infinito não trava a interface. Python e JavaScript têm cada um o seu iframe; o JavaScript usa um worker novo por execução, e o Python, um worker que dura enquanto o iframe durar. O SQL roda no `sqlite3` do Pyodide, no mesmo worker do Python.
- **Sem rede.** A política da página de execução tem `connect-src 'none'`, e os workers criados de `data:` herdam essa política (medido no Chromium): `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `pyodide.http` e `from js import fetch` são barrados antes de sair. O que sobra são pedidos GET para o próprio site: `import()` e `importScripts` num worker aninhado (`script-src 'self'`) e, se algum código chegasse à thread do iframe, a navegação do próprio iframe. Medido no Chromium, todos saem da origem `null` sem o cookie da sessão, e a resposta não pode ser lida (a da API ainda é barrada por `X-Frame-Options: DENY` quando o iframe navega até ela).
- **Protocolo.** A página de execução cria um `MessageChannel` e manda uma ponta dele junto com o aviso de que está pronta (`postMessage` para o pai). O site só aceita esse aviso se `event.source` for o `contentWindow` do seu iframe, se o formato e a versão baterem e se ele trouxer um valor aleatório que o site pôs no fragmento da URL do iframe (`runner.html#<valor>`). Esse valor existe porque quem emoldura o site (no GitHub Pages, qualquer página pode) consegue trocar a página do iframe por outra, que tem o mesmo `contentWindow`, mas não consegue ler a URL do iframe. Pelo mesmo motivo o site nunca escreve no `contentWindow`: a página lá dentro pode ter sido trocada depois do aviso. Daí em diante tudo passa pelo canal. Cada pedido leva um id; uma resposta só vale se o id for o do pedido em andamento e o formato estiver certo, e o resto é ignorado. Um pedido por vez em cada iframe.
- **Tempo limite do lado do site.** JavaScript 5 s, Python e SQL 8 s, início do Python 90 s, resposta do iframe 20 s, download do Pyodide 5 min. Ao estourar, o site **destrói o iframe** (o que encerra os workers e qualquer tarefa assíncrona deixada pelo estudante) e o próximo pedido cria outro. Depois de cada execução Python, as tarefas `asyncio` pendentes são canceladas, para não vazarem para a execução seguinte; callbacks agendados pelo módulo `js` (por exemplo `setTimeout` com `create_proxy`) não são cancelados e só acabam quando o iframe é destruído.
- **Falha não é permanente.** Se o download ou o início do Pyodide falha, o iframe é descartado e a próxima execução tenta tudo de novo. O wasm é conferido com `WebAssembly.validate` antes de o Pyodide carregá-lo, então um arquivo corrompido falha na hora, e não depois de 90 s. O mesmo vale depois do início: se o worker do Python cai (um callback do estudante que lança erro derruba o worker entre uma execução e outra), qualquer falha que não seja o tempo limite descarta o iframe, e a próxima execução inicia o Python de novo. Uma mensagem do worker do Python que não responda a um pedido (o código do estudante consegue mandá-las com `from js import postMessage`) encerra o Python na hora: numa enxurrada dessas mensagens, medida no Chromium, a página do site chegou a levar mais de 1 s para responder, porque a thread do iframe é a mesma dela.
- **O laboratório não mexe na correção.** O Python dura enquanto o iframe durar, e o código do estudante consegue deixá-lo alterado: trocar a função que corrige (`__main__.run`), gravar arquivos no sistema de arquivos virtual (o `ATTACH DATABASE` do SQL também cria arquivos), agendar callbacks. No laboratório entra código de qualquer pessoa (link `#codigo=`), e um teste e2e mostrou que esse código fazia o desafio de uma lição, aberto depois na mesma aba, "passar" com o código errado, o que entra no progresso. Por isso as execuções do laboratório (Python, passo a passo e SQL) vão marcadas, e o site nunca manda uma execução sem a marca para um iframe que já rodou uma com ela: o iframe é recriado antes. A conferência é feita na hora do envio, dentro da fila de pedidos, e não na hora da chamada: antes, com o Python ainda iniciando, um pedido do laboratório ainda na fila podia rodar no iframe novo, e o desafio testado logo depois aparecia como resolvido (teste e2e). Entre exercícios das lições isso não é feito: lá o código é da própria pessoa.
- **Teto na fronteira** (`apps/web/src/features/runner/limits.ts`). Tudo o que volta do iframe é tratado como entrada hostil: o formato é conferido e cada texto (stdout, mensagem e traceback de erro, mensagem de teste, saída guardada em cada passo) é cortado em 65.536 caracteres, com o aviso "saída cortada: passou de 65.536 caracteres". O passo a passo inteiro tem teto de 1.000 passos e 16 × 65.536 caracteres (a interface avisa "passo a passo cortado"); o resultado SQL, de 1.000 linhas e 200 colunas, e as duas tabelas (resultado e esperado) juntas, de 16 × 65.536 caracteres e 20.000 células, com linhas inteiras (antes, 200 linhas × 200 colunas de 1.000 caracteres deixavam uma tarefa de 17 s na página ao desenhar a tabela; teste e2e); nomes, tipos e valores de variáveis, de 1.000 caracteres. Uma saída de 1 milhão de caracteres chega cortada e a página continua respondendo (teste e2e). A explicação do erro, que roda na página do site, só aplica as expressões regulares ao primeiro milhar de caracteres da mensagem (`errors.ts`): antes, uma mensagem de 65.536 letras levava cerca de 4 s em cada uma das piores expressões e travava a página por quase 9 s (medido no Chromium; teste e2e e de unidade). Dentro dos workers também há limite de 65.536 caracteres (`harness.py` e `output-limit.ts`, no `js.worker.ts`), que interrompe o programa com o aviso "Saída limitada a 65536 caracteres"; ele evita juntar a saída inteira na memória do worker, mas não é garantia, porque o código do estudante fala direto com a página de execução (`postMessage`) sem passar por ele. A garantia é o teto na fronteira, e há teste e2e com um resultado forjado de 1 milhão de caracteres.
- **Aberta diretamente, não executa.** No servidor, `/runner.html` sai com `Content-Security-Policy: sandbox allow-scripts; ...`, então mesmo aberta como página normal ela tem origem opaca. Em qualquer hospedagem, `runner.js` se recusa a rodar se a própria origem não for `null` (aberta sem a CSP do servidor, como no GitHub Pages), se não estiver num iframe, ou se `location.ancestorOrigins` (onde o navegador oferece) disser que quem a emoldura é outra origem.
- **O cache.** Medido no Chromium 141: as requisições de um iframe de origem opaca **não usam o cache HTTP**; cada iframe novo e cada recarga baixariam de novo os 13,5 MB do Pyodide. Por isso quem baixa os arquivos do Pyodide (e o código dos workers e o `harness.py`) é o site, na origem dele, com cache, e os entrega ao iframe como `ArrayBuffer` transferido; o worker importa os módulos do Pyodide de URLs `blob:` e serve o wasm e a biblioteca padrão a partir desses bytes. Com isso, um iframe recriado depois de um tempo limite e a recarga da página não baixam de novo nada de `/pyodide/`: o site lê do próprio cache HTTP (cerca de 65 ms na medição local).
- `'unsafe-eval'` (o `new Function` do JavaScript do estudante) e `'wasm-unsafe-eval'` (Pyodide) existem só na política da página de execução, que não tem nada a proteger. A política do site não tem nenhum dos dois.
- O link de compartilhamento do laboratório guarda o código no fragmento (`#`) da URL, que nunca vai ao servidor, e abrir um link compartilhado não executa nada até a pessoa clicar em executar.

Os testes de ponta a ponta em `e2e/isolamento.spec.ts` (Chromium real, servidor real, conta logada) fazem os ataques acima em JavaScript e em Python (`fetch` com e sem `credentials: 'include'` e com `x-alicerce`, `XMLHttpRequest`, `pyodide.http`, `import()`) e conferem que a conta continua existindo, que o progresso não mudou, que o e-mail não aparece na saída e que nada saiu com o cookie. Um dos testes desliga a CSP (`bypassCSP`) para provar que a origem opaca protege sozinha. Outros conferem `WebSocket`, `EventSource`, `importScripts`, worker com URL do site e `POST` `no-cors` sem `x-alicerce` (com e sem CSP); o que acontece se um código chegasse à thread do iframe (`window.open`, `top.location`, formulário, imagem da API, navegação do próprio iframe, um segundo aviso de "pronto"); `localStorage`, cookies, IndexedDB e `parent.document`; a página de execução aberta diretamente; laço infinito em Python e em JavaScript; falha no download e no início do Pyodide seguida de sucesso; queda do worker do Python e enxurrada de mensagens seguidas de uma execução normal; um resultado forjado pelo próprio código do estudante (gigante ou malformado); um link do laboratório que tenta mudar a correção de um desafio feito depois; e a saída de 1 milhão de caracteres. `e2e/pages.spec.ts` usa o build estático (`BASE_PATH=/alicerce/ VITE_STATIC=1`) servido sem cabeçalhos de segurança e confere que o código do laboratório fica sem rede e sem os dados do site, que a página de execução aberta direto ou emoldurada por outra origem não roda, que uma página que emoldura o site e troca a página do iframe de execução não recebe o canal, que um exercício de Python de uma lição gratuita roda e é corrigido e que JavaScript roda no laboratório (no build público não há exercício de JavaScript; a correção de um deles, de lição Premium, é testada no servidor).

### Limites que continuam valendo

- **A correção local não tem integridade.** O código do estudante roda no mesmo worker que o corretor (`harness.py` e os testes do exercício) e pode forjar um resultado "passou" no formato certo; o site só confere formato e tamanho. O progresso salvo no navegador também está nas mãos da pessoa. Nenhuma certificação, nota ou recompensa pode depender da correção feita no navegador: para isso, a correção teria de rodar de novo num ambiente que o estudante não controla.
- **O isolamento é de origem, não de recursos.** O código do estudante não age em nome da pessoa, mas pode gastar CPU até o tempo limite e memória até o navegador intervir. Não medimos se o Chromium põe o iframe num processo separado, nem o que acontece com estouro de memória.
- **Medido só no Chromium.** Os testes rodam no Chromium do Playwright. Firefox e Safari não foram testados. Onde o navegador não oferece `location.ancestorOrigins` (segundo a documentação da MDN, o Firefox não oferece; não conferido aqui), a conferência de quem emoldura a página de execução depende só do `frame-ancestors` do servidor (que não existe no GitHub Pages). Mesmo emoldurada por outro site, a página de execução continua com origem opaca: no máximo alguém usa a CPU do visitante para rodar código sem acesso a nada.
- **GitHub Pages.** A demonstração fica em `https://arthurmontinegro.github.io/alicerce/`, mesma origem de todos os sites Pages do dono, e o Pages não deixa configurar cabeçalhos: não há CSP, `frame-ancestors` nem `X-Frame-Options` vindos do servidor. Lá a proteção da execução vem só do que está nos arquivos: o atributo `sandbox` do iframe, a CSP em `<meta>` do `runner.html` (que vale também para os workers) e a conferência de origem do `runner.js`. O resto do site não tem CSP no Pages, e qualquer outro site do dono na mesma origem consegue ler o `localStorage` da demonstração (inclusive o progresso em `alicerce:progresso:v1`); isso não é resolvido aqui. No Pages, `'self'` da CSP da página de execução também cobre os outros sites do dono, então o código do estudante consegue fazer `import()` deles (sem credenciais e rodando na origem opaca). Sem `frame-ancestors`, qualquer página pode emoldurar a demonstração; o protocolo impede que ela receba o canal da execução trocando a página do iframe, mas não impede que ela atrapalhe: trocada a página, a execução não começa e o site só avisa depois de 20 s. O comportamento do Pages usado nos testes (sem CSP, `Access-Control-Allow-Origin: *` em tudo) é **suposição**, imitada por `e2e/servidor-pages.ts`, não medição do github.io.

## Cabeçalhos

Toda resposta leva (`apps/api/src/security.ts`):

- `Content-Security-Policy`: `default-src 'self'`, `script-src 'self'` (sem `eval` e sem WebAssembly: o código do estudante não roda nesta origem), `connect-src 'self'`, `frame-src 'self'` (o site só emoldura a própria página de execução), `worker-src 'none'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'self'`. Não há script inline: o script de tema vive em `/theme.js`.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Cross-Origin-Opener-Policy` e `Cross-Origin-Resource-Policy: same-origin`, `Permissions-Policy` desligando câmera, microfone, localização, pagamento e USB.
- `Strict-Transport-Security` em produção.
- `Cache-Control: no-store` em toda a `/api`.

Exceções, só para a página de execução:

- `/runner.html` recebe outra CSP: `sandbox allow-scripts` (origem opaca mesmo aberta diretamente), `default-src 'none'`, `script-src 'self' blob: 'unsafe-eval' 'wasm-unsafe-eval'`, `worker-src data:`, `connect-src 'none'`, `base-uri 'none'`, `form-action 'none'` e `frame-ancestors 'self'` (só o próprio site a emoldura), além de `X-Frame-Options: SAMEORIGIN`. O caminho é comparado depois de decodificado, porque o servidor de arquivos também atende `/runner%2Ehtml`.
- `/runner.js` recebe `Cross-Origin-Resource-Policy: cross-origin`: para a página de execução, de origem opaca, ele é um arquivo de outra origem, e com `same-origin` o Chromium o bloqueia. É um script clássico, carregado sem CORS, então não precisa de `Access-Control-Allow-Origin`. Nenhum outro arquivo precisa de exceção, porque o Pyodide, o código dos workers e o `harness.py` são baixados pelo site e entregues ao iframe.
- Nada em `/api` recebe CORS ou `Cross-Origin-Resource-Policy: cross-origin` (há teste para isso em `apps/api/test/api.test.ts`).

## Contas e sessões

- Senhas com scrypt (N=32768, r=8, p=1) e sal aleatório por usuário; comparação em tempo constante.
- Regra de senha no estilo NIST 800-63B: mínimo de 10 e máximo de 200 caracteres, sem exigir símbolos.
- Login com e-mail inexistente também calcula um hash (de uma senha fictícia), para que o tempo de resposta não revele quais e-mails têm conta.
- Mensagem de erro de login genérica.
- Sessão: token aleatório de 256 bits, guardado no banco apenas como SHA-256. Cookie `HttpOnly`, `SameSite=Lax`, validade de 30 dias. `Secure` vem ligado com `NODE_ENV=production`; `COOKIE_SECURE`, quando tem valor, decide em qualquer modo: `1`, `true`, `yes` ou `sim` (sem diferenciar maiúsculas) ligam, qualquer outro valor desliga, e vazia vale como não definida (`apps/api/src/config.ts`). Sessões vencidas são apagadas a cada login.
- `POST /api/auth/sessions/encerrar` ("Sair de todos os aparelhos", em Conta) apaga todas as sessões da conta, inclusive a atual, e limpa o cookie; `ended` conta as que ainda valiam. Exige uma sessão válida. Num outro aparelho com o site aberto, a próxima sincronização recebe 401 e o navegador passa a visitante.
- Excluir a conta (`DELETE /api/auth/me`) exige a senha atual no corpo, além da sessão: um cookie esquecido num computador emprestado não basta para apagar tudo. A senha passa pelo mesmo scrypt e pela mesma comparação em tempo constante do login; sem senha a resposta é 400 (sem gastar tentativa), com senha errada é 403. As tentativas contam no limite por IP da exclusão e no mesmo balde por conta do login, então palpites de senha somam, venham de onde vierem.
- Excluir a conta apaga usuário, sessões, progresso, histórico de planos e uso do tutor (cascata).
- No navegador, cada conta e o visitante têm chaves próprias para o progresso e os rascunhos (`alicerce:progresso:v2:<perfil>` e `alicerce:draft:v2:<perfil>:`, em `apps/web/src/state/store.ts`). Entrar não importa o progresso de visitante, e trocar de conta numa aba troca as outras (`alicerce:auth-change`). Testes em `e2e/contas.spec.ts`: visitante, duas contas e de novo a primeira na mesma aba, e a troca entre duas abas, sem misturar progresso nem rascunhos, nem no servidor.
- Saída que o servidor não confirmou (sem rede, por exemplo): a conta some da aba na hora, e a pendência fica gravada (`alicerce:saida-pendente`). Com ela, as outras abas também escondem a conta, e recarregar a página tenta sair de novo em vez de entrar com o cookie que ainda vale; o aviso do topo tem o botão "Tentar encerrar sessão", e a volta da conexão tenta sozinha. Antes de 21/10/2026, a pendência ficava só na memória da aba: recarregar trazia a conta de volta e as outras abas continuavam mostrando os dados dela. Se o navegador não deixa gravar, a pendência vale só na aba aberta.

## CSRF

Toda requisição que muda estado exige o cabeçalho `x-alicerce: 1`. Formulários de outro site não conseguem enviar cabeçalhos personalizados sem passar por CORS, e o servidor não habilita CORS. Isso se soma ao `SameSite=Lax`, que não separa portas nem subdomínios do mesmo site: um formulário em `127.0.0.1:outra-porta` leva o cookie (teste e2e), e quem barra é o cabeçalho.

A conferência vale para qualquer caminho, e a decisão sobre o que é API usa a rota escolhida pelo roteador, não o texto cru da URL. Antes, ela olhava `startsWith('/api/')` na URL crua, e o roteador decodifica o caminho: `DELETE /%61pi/auth/me` sem o cabeçalho apagava a conta, e um formulário do mesmo site encerrava a sessão com `POST /%61pi/auth/logout` (há testes em `apps/api/test/api.test.ts` e em `e2e/isolamento.spec.ts`). Do iframe de execução isso não funcionava, porque de lá o cookie não vai.

Essa defesa vale contra outros sites, não contra código que roda na origem do próprio site: esse código envia o cabeçalho e o cookie sem esforço. É por isso que o código do estudante roda numa origem opaca (ver "Execução de código do estudante"); para a API, um pedido de lá é de outra origem, sem cookie e sem CORS.

## Limites de uso

| Alvo | Limite |
|---|---|
| Toda a `/api` | 600 requisições por minuto por IP |
| Login | 10 por 15 minutos por IP e, separadamente, por e-mail |
| Cadastro | 10 por 15 minutos por IP |
| Excluir a conta | 10 por 15 minutos por IP e, por conta, somadas às tentativas de login dessa conta |
| Sincronizar o progresso (`PUT /api/progress`) | 60 por minuto por conta, conferidas antes de ler o corpo |
| Tutor | 12 por minuto por conta; sem conta, por IP |
| Tutor com IA | só para contas com Premium ativo: 20 perguntas por dia, dentro de 200 por mês (mês do calendário em UTC); `TUTOR_DAILY_LIMIT` só reduz o diário. Teto do Alicerce todo: `TUTOR_GLOBAL_DAILY_LIMIT` chamadas por dia (padrão 300). Conta gratuita e visitante usam o tutor local |

Corpos de requisição têm no máximo 1 MB, exceto `PUT /api/progress`, que aceita até 4 MiB: o maior progresso legítimo (5 000 tentativas e 5 000 revisões, o teto do saneamento, com todo o catálogo estudado) mede cerca de 2,5 MB, e o teste `apps/api/test/contas.test.ts` gera esse caso e confere a folga. Essa rota confere a sessão e o limite por conta antes de ler o corpo: sem conta, ou acima do limite, o corpo é descartado sem ser guardado nem interpretado. Ler, sanear, mesclar e gravar um envio no maior caso legítimo custa cerca de 300 ms de CPU (medido num teste local com `app.inject`; a maior parte é a mesclagem), e o limite por conta impede que uma conta só ocupe o servidor; várias contas no mesmo IP ainda conseguem, dentro do limite geral. Atrás de um proxy reverso, o limite de corpo do proxy também precisa aceitar 4 MiB nessa rota (no nginx, `client_max_body_size` vale 1 MB por padrão).

## Progresso sincronizado

O documento de progresso vem do navegador e é tratado como entrada hostil (`packages/engine/src/progress.ts`, `sanitizeProgress`): só campos conhecidos são copiados, chaves como `__proto__`, `constructor` e `prototype` são descartadas, números são limitados à faixa válida e listas e mapas têm tamanho máximo.

## Tutor com IA

- A chave fica só no servidor, em variável de ambiente.
- A solução oficial do exercício nunca é enviada ao modelo.
- O código e o erro do estudante vão delimitados por tags, como dados; as regras pedagógicas ficam no prompt de sistema, que o estudante não controla.
- Qualquer erro, recusa ou estouro do limite cai no tutor offline, sem expor detalhes do erro.
- Além das cotas por conta, um teto de chamadas por dia no Alicerce todo (`TUTOR_GLOBAL_DAILY_LIMIT`, padrão 300) limita o gasto mesmo com muitas contas Premium; os totais do dia (chamadas, falhas e tokens) ficam em `tutor_ai_daily`, sem dados de contas.

## Privacidade

Sem conta, nada sai do navegador além das perguntas ao tutor offline (que não guarda nada). Com conta, o servidor guarda e-mail, nome opcional, hash da senha e o progresso. Não há rastreadores, anúncios ou scripts de terceiros. Detalhes em `/privacidade`.

Os backups do banco têm os mesmos dados, inclusive de contas excluídas depois de cada backup, até saírem da retenção. Eles nascem legíveis só pelo dono (`0600`, numa pasta `0700` quando o script a cria). Guarde-os cifrados fora da máquina ([Operação](OPERACAO.md)).

## Pontos conhecidos

- `style-src 'unsafe-inline'` existe porque alguns componentes usam `style={...}` do React. O risco é baixo (não há injeção de HTML), mas o ideal é remover.
- O limitador de requisições é em memória: vale para uma instância. Com várias réplicas, precisa de um armazenamento compartilhado.
- `TRUST_PROXY` só deve ser ligado atrás de um proxy conhecido; ligado sem proxy, o IP usado nos limites pode ser falsificado.
- O cadastro responde 409 "Já existe uma conta com esse e-mail", o que revela quem tem conta. Resolver exige confirmar o e-mail (responder igual nos dois casos e avisar por e-mail), e ainda não há provedor de envio de e-mail; o mesmo vale para recuperar senha.
- Não há troca de senha nem lista das sessões abertas por aparelho; "Sair de todos os aparelhos" encerra todas de uma vez.
- A execução do código do estudante tem limites próprios (correção sem integridade, GitHub Pages com origem compartilhada, testes só no Chromium): ver "Limites que continuam valendo", acima.
